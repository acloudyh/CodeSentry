CodeSentry 技术调研与讲解手册

本文用于讲解本地代码安全审核的方法与产品操作。完整技术依据见技术调研方案总结，实施与核验要求见本地代码安全审核技术调研与实施流程。

1. 方案定位

从已有本地仓库或标准 Git 地址取得代码，固定审核版本，组合使用开源工具发现风险线索，再由审核人员结合业务、调用链和部署条件确认问题，形成整改与核验记录。

产品采用 Java 模块化单体、Vue 操作台、MySQL 和本地文件存储。选择这一架构的原因是部署组件少、适合现有 Java 团队维护，并且能自主控制批次、复核与报告流程。GitLab 仅提供代码，不依赖其流水线和安全能力。

扫描和结果存储在本地完成。启用外部复核服务时，必要源码证据会提交到配置接口，应按项目约定执行。

讲解时抓住四个关系：Git 固定输入版本，扫描工具提供线索，工具复核与人工审核分别保存结论，报告按统一口径筛选结果。

3. 审核实施流程

人工审核有独立环节：抽查源码、追踪调用链、检查权限与防护，确认风险或误报并记录依据；准备、报告审定和修复核验也由人员完成。工具复核只提供辅助建议，不能代替这些工作记录。

阶段 主要工作 形成结果
准备 确认范围、取得只读权限、固定 Commit 审核版本与排除范围
检查 全量或增量扫描、工具复核、人工抽查与调用链分析 候选结果与人工判断依据
交付 筛选报告、依赖整改归组、列明确认状态 整改清单与报告
核验 拉取修复版本，复查根因与关联路径 通过、未通过或待验证结论

全量用于首次审核或重大变更；增量分别扫描当前版本与所选分支的共同祖先，再比较新增、存量及已修复条目。增量检查仍需人工关注变更影响的上下游，规则不再命中也不能单独证明修复完成。

分支快照使用 git archive，不切换原仓库分支。当前工作区模式可以包含未提交内容，两种方式均须说明实际输入范围。

4. 五类工具如何分工

工具 检查对象 主要作用与边界
Semgrep 源码、配置、JSP 等受规则支持的文件 代码模式与自定义规则；覆盖范围取决于规则包
Gitleaks 工作目录或扫描快照 疑似硬编码凭据；不代表扫描完整 Git 历史
Trivy 可识别依赖与文件 组件版本、已知 CVE、密钥；依赖本地漏洞库及组件元数据
SpotBugs / FindSecBugs 已有 JAR 中的 Java 字节码 补充老项目检查；需配置业务包范围
Alibaba P3C-PMD Java 源文件 阿里编码规范检查；规范问题不直接等同于安全漏洞

JSP 本地规则包括路径穿越、命令执行和开放重定向。没有 Java 源文件时，P3C 零结果不代表规范全部通过；当前不会自动编译 JSP 或重建业务项目。

前端有独立的本地专项规则包：JS/TS/JSX/TSX 检查跨窗口消息、浏览器输入跳转、敏感凭据存储和明文 HTTP；Vue 以限定模式检查路由参数直出 HTML、跳转、消息及凭据存储。它随本地及综合规则集执行，React 复用 JS/TS 源码规则，Vue 不提供完整跨文件分析。压缩与部分第三方脚本仍排除，eval 和直接 innerHTML 规则不重新启用。

规则覆盖和排除清单在扫描前确认。指定规则被忽略不代表相关风险不存在。当前规则范围与待验证项集中见技术总结。

5. 问题、审核组与整改组

名称 含义 计数用途
候选问题条目 扫描结果，经复核后可能是风险或误报 台账查询
审核组 相同依赖文件、组件坐标和安装版本的 CVE 集合 工具复核执行进度
报告漏洞条目 通过报告筛选的条目，不代表全部经人工确认 报告统计，结合人工状态解读
整改组 报告中合并展示的同文件、同组件版本问题 组织升级动作与整改展示

例如：同一 POI JAR 的 6 个 CVE 可形成 1 个审核组，共用一次初审和一次复审；若 6 条均通过报告筛选，则报告统计仍为 6 条，展示为 1 个整改组，并保留各 CVE、证据和结论。不同文件或版本分别处理，非依赖代码问题不按组件归组。

再次执行工具复核时按最新状态跳过成功项；失败或中断项可重试。任务支持停止，失败显示实际原因。人工可逐条复核，也可只对已勾选的问题执行批量人工复核。

6. 报告如何形成

报告区分两种结果：

  • 已确认风险：审核人员已提交确认结论。
  • 待人工确认项：工具初审和复审完整完成、每次可信度均大于 65% 且未判为误报，但尚未人工确认。

人工误报不进入报告。未审核、执行失败、恰好 65% 或低于门槛的工具结果不自动进入报告，保留在台账继续处理。工具门槛是筛选条件，不是漏洞成立概率，也不替代人工确认。

正式对外交付前，审核人员检查待确认项并明确交付范围；如只交付已确认漏洞，应先完成确认。产品当前允许符合工具门槛的待确认项进入报告，讲解时须说明其状态。

报告支持在线查看、Word 和 PDF 下载，列表按扫描时间倒序排列。源码问题展示文件与行号；依赖漏洞展示 JAR、组件版本及 CVE，并注明无源码行号。Word/PDF 正文用宋体，标题和表头用黑体并嵌入字体。

报告生成不修改原始记录，但重新导出会读取当时的复核状态；需要保留交付版本时，应归档已导出的文件。

7. 页面操作顺序

页面 建议操作
仪表盘 查看仓库、扫描与风险概况
代码仓库 登记或编辑本地目录、远程地址及默认分支
扫描规则 确认本地、社区或综合规则集及排除范围
发起扫描 选择全量或增量、工作区或快照、目标及基线
扫描记录 查看详情、日志、工具状态，跳转对应批次台账，必要时停止
问题台账 按批次筛选，查看原始内容，执行工具复核和人工复核
整改报告 检查统计与确认状态，在线查看或下载
工具管理 维护复核服务配置、启停及默认工具
系统设置 查看节点与扫描器配置状态

扫描记录和台账默认每页 20 条，可选 50、100、500 条并选择页数。工具批量审核面向当前批次，人工批量复核只处理已勾选的问题。

8. 配置与运行维护

工具管理支持配置增删改查。服务配置存入 MySQL，接口密钥加密保存且不回显明文；备份与恢复应同时覆盖数据库及本地加密主密钥文件。“已配置”只代表配置存在，是否可调用以实际接口响应为准。

Docker Compose 编排前后端，后端镜像集成扫描工具、插件和字体，前端由 Nginx 提供服务；MySQL 连接主机既有实例。仓库只读挂载，快照、报告、漏洞库等持久化。时间统一按东八区处理。

Trivy 扫描读取本地缓存，漏洞库与 Java 索引库通过独立脚本维护。脚本已实现，定时调度、互斥和通知待实施。更新周期、失败重试与缓存要求统一见漏洞库维护设计。

10. 常见问题

工具命中就是漏洞吗？
不是。需要判断版本、可达路径、输入控制、权限、现有防护和部署条件。P3C 还可能给出编码规范问题。

合并依赖问题是否丢失 CVE？
审核和报告按组处理，仍保留成员 CVE、位置和复核证据；组数与漏洞条目数分别解释。

完全离线能否检查？
需预先准备工具、本地规则与漏洞库，并使用本地复核服务。社区规则和外部复核接口的网络要求应单独确认。

停止、失败是否等于没有问题？
停止表示任务未完整执行；部分完成表示部分工具没有成功。应结合日志与覆盖范围解释结果。

更新漏洞库会自动改变旧报告吗？
不会自动重扫历史代码。使用新库检查应发起新批次；历史交付文件应独立归档。

修复后规则不再命中是否算通过？
还需人工核查根因、关联路径与绕过条件，形成明确核验结论。
